Real-time voice on the Live API

Live Translator, taken apart  ·  August 2026
Google Cloud
A working open-source app — github.com/kazunori279/live-translator — used as the worked example throughout. Everything in this deck is either in the Live API docs or was measured on that app in hour-long soak tests.
01
The app
What it does, and the two ways it can do it.
Google Cloud
Fifteen minutes, three parts: the app first so the rest has something to point at, then the API underneath it, then what an hour of real use taught us.
Two people, two languages, one laptop
Live Translator is a browser page and a small Python server. You pick a language pair, hit start, and talk — it speaks the other side back out loud and puts both transcripts on screen.
Conversation mode
One interpreter, both directions. Speak either language and it answers in the other — 97 to choose from.
Simultaneous mode
A translate-specialised model that starts speaking while you are still talking. Half a second behind, 78 languages.
Your own glossary
A CSV of terms, steered into the model so it says them and rewritten into the captions so you read them.
Push to talk
Hold the button to send. The microphone stops at the client, so the rest of the room never reaches the model.
Caption overlay
A second window at /caption with nothing but the running text, sized for a projector behind the speaker.
Voices and devices
30 prebuilt voices, and ranked microphone and speaker preferences that survive a reload.
Google Cloud
Worth demoing live if you can: the interesting moment is interrupting it mid-translation and watching it stop. That is the Live API’s barge-in, not anything this app implements.

The glossary is two mechanisms wearing one name — it goes into the system instruction so the model says your term, and it runs a second pass over the transcript so the viewer reads it. The second pass is harder than it sounds: transcripts stream in fragments that split words down the middle, so the rewriter has to buffer across message boundaries before it can match a term at all.
One app, two model configurations
Same app, same server. A mode is a different model and a different way of steering it.
ModeModel and steeringWhat you give up
Conversation gemini-3.1-flash-live-preview — bidirectional interpreter system instruction, glossary embedded both ways ~5.5 s from speech-end to a finished turn
Simultaneous gemini-3.5-live-translate-preview — translationConfig only, source language auto-detected No prompt, no tools, no glossary steering
The translate model accepts no system instruction, no tools and no function calling. Anything you would normally prompt for has to become a config field instead — echoTargetLanguage is that mode’s entire echo policy.
Google Cloud
The trade is stark and worth stating out loud: simultaneous answers in ~0.5 s because it emits while the speaker is still talking, but it cannot be told anything. Conversation waits for the turn to end, and in exchange you get 97 languages, a glossary, and an instruction the model actually follows.
02
Gemini Live API
What is underneath it, and how this app uses it.
Google Cloud
Everything in this section is in the public docs. The point of going through it is that the shape of the API decides the shape of your app — the next section is entirely consequences of what is on the next five slides.
The challenge — three models in a chain
Real-time voice used to mean a chain: speech-to-text, then a text model, then text-to-speech. Every hop waits for a whole utterance before the next can start.
Google Cloud
This is how nearly every voice assistant was built until recently, and it is still the right shape for plenty of things — it is just the wrong shape for a conversation. Each box is a separate model with its own turn boundary, so the round trip cannot start until the one before it has finished a whole utterance.

The killer is not the raw milliseconds, it is the second box: a text model needs a complete sentence before it can begin. That single constraint is what forces the pause, and it is what the next slide removes.
The solution — one native-audio model
Gemini Live API replaces the chain with one speech-native model on one open connection — a setup frame, then audio in both directions until someone hangs up.
Google Cloud
VAD is tunable — startOfSpeechSensitivity, endOfSpeechSensitivity, prefixPaddingMs, silenceDurationMs — or you can switch to manual turn control with activityStart / activityEnd. Live Translator’s push-to-talk button is a client-side variant: it stops sending frames rather than signalling activity.
What the open connection gives you
The Gemini Live API is a speech-native model you hold a connection to. Not a request and a response — a session that stays open while both sides talk.
Native audio, both ways
16-bit PCM up at 16 kHz, down at 24 kHz. Nothing is flattened to text in the middle, so tone, pace and interruption survive. Transcripts are one config field away.
The model runs the turn
Server-side voice activity detection decides when you stopped speaking, and barge-in cancels a reply in flight. Or take manual control with activityStart and activityEnd.
Reach, and tools
97 languages and 30 prebuilt voices. Function calling, code execution and Search grounding all work mid-conversation, without dropping the call.
Two front doors, one wire protocol. Gemini API takes an API key, or an ephemeral token straight from the browser, and is the shortest path to something that talks back. Gemini Enterprise Agent Platform adds IAM, VPC-SC, data residency and regional endpoints. Porting between them is an auth change, not a rewrite.
Google Cloud
Agent Platform is the product formerly known as Vertex AI; the console menus and docs moved in 2026. Same LiveConnectConfig, same message shapes; the Gen AI SDK picks between them from GOOGLE_GENAI_USE_VERTEXAI.

One gotcha worth naming out loud: Live Translator clears GOOGLE_GENAI_USE_VERTEXAI at import time to pin itself to the API-key route. If you inherit that variable from your environment and don’t notice, you will spend an afternoon wondering why your Vertex quota looks idle.

Transcription deserves a sentence: asking for it costs no extra latency, because the model emits it alongside the audio it is already generating. That is what lets a translation app speak and caption from a single pass.
Audio is where we stopped, not where it stops
Live Translator uses one modality and a fraction of what a session offers. The same socket, unchanged, carries the rest.
Video on the same socket
One frame per second at 768×768, interleaved with the audio. The user shows you the leaking valve instead of describing it — no second channel, no second connection.
It hears how you said it
Native-audio models add affective dialog, where tone and mood shape the reply, and proactive audio, where the model decides to speak up instead of waiting to be addressed.
Past the fifteen minutes
Context window compression trims the oldest turns and lifts the duration cap. Session resumption hands back a token that restores history after a dropped connection.
None of these is a rewrite — each is a field in the same LiveConnectConfig. The application shapes follow from there: a support agent watching a customer’s camera, a field technician on smart glasses working hands-free, a shopper holding a garment up to the webcam.
Google Cloud
Live Translator uses none of these three, which is exactly why they are worth showing: the ceiling is a long way above one app’s use of it.

A caveat on the third card. Live Translator deliberately does not use session resumption. Resuming replays the tail of the conversation, and an off-by-one in what got re-delivered cascaded into duplicated audio; replacing the session outright measured far better — 98% turn completion against 65%. Compression and resumption are the right tools for an assistant that has to remember. They were the wrong tools for an interpreter that only has to keep up.

1 fps at 768×768 is the documented recommendation, not a hard ceiling. Proactive audio and affective dialog are native-audio-model features and are not available on every Live model — check the model card before you promise them.
How this app holds that socket
Three files, one relay. The browser captures and plays, and does nothing else. Every decision — session lifetime, the system instruction, the API key — stays server-side.
Google Cloud
Both audio paths are AudioWorklets, not ScriptProcessorNode — capture runs in an AudioContext pinned to 16 kHz and playback in a separate one pinned to 24 kHz, because the Live API’s two rates are different and resampling in JavaScript is not worth it. The recorder converts Float32 to Int16 by multiplying by 0x7fff; that one line is the whole codec.

The two coroutines are the design: upstream_task only ever writes to whichever session is current, and session_loop owns opening and retiring sessions. Neither knows about the other’s timing, which is what makes the session handover in section 03 tractable.

Why a relay at all, when client-to-server is lower latency? The system instruction and glossary stay server-side, session churn stops being the client’s problem, and the API key never leaves the container.
03
In production
What an hour of real use does to a live session.
Google Cloud
None of this shows up in a demo. It shows up within the first ten minutes of a real conversation, and it was found by soak-testing rather than by reading.
One client socket, many model sessions
Audio-only Live sessions cap out at 15 minutes. The user’s browser tab doesn’t.
Google Cloud
Why relay at all, when client-to-server is lower latency? Three reasons here: the system instruction and glossary stay server-side, session churn stops being the client’s problem, and the API key never leaves the container. If you go client-direct, use ephemeral tokens — and note they can pin translationConfig so the user can’t retarget the language.

Session resumption is offered by the API (handles valid 2 hours). It was removed from this app because it caused an off-by-one cascade — the model prepending the previous turn’s translation. 98% pass rate without it, 65% with.
GoAway gives you fifty seconds
Observed every ~9 minutes, always with time_left=50s. What you do with the notice decides whether the listener hears the seam.
Google Cloud
Both timers are measured from the last frame actually forwarded to the browser, so a turn genuinely in flight is never clipped. What gets replayed is exactly the audio captured since the outgoing session last said anything — everything older was already translated.

If a stalled drain recovers and finishes its turn after all, the mirrored replacement is thrown away and a fresh one opened: it heard audio the old session went on to answer, so keeping it would translate the same words twice. Across 11 observed GoAways, that was the most common path.

Watch the turn accounting: a synthetic turnComplete is a boundary with no turn behind it. Anything pairing utterances 1:1 with boundaries will sit one turn behind forever. The soak harness did exactly this and reported 68% while translation was perfect.

Twelve GoAways, every one clean. The upstream closed 31 times with 1008 policy violation and the retry loop absorbed 30 of them invisibly. Simultaneous is judged harder, not hosted worse: it commits to output while the speaker is still talking and carries no system instruction to steer terminology.
Google Cloud
The two latency columns are not the same measurement and should never be read as one mode being ten times faster at the same job. Conversation waits for the turn to end before it answers; simultaneous emits while you are still speaking, so its first response lands at 0.00 s by construction.

The recovery numbers are the ones to steal: connect timeout 10 s, retry backoff 0.2 s doubling to a 4 s cap, reset after a successful session. Before that fix, production logs showed ~20 errors per 24 hours; after, 1 error in 15 hours.
If you’re building one of these
Relay through your own server unless you can mint ephemeral tokens
Treat session expiry as part of the protocol, not as an error
Buffer streamed transcripts across fragment boundaries before touching them
Assume the speakers reach the microphone, and defend in more than one layer
Retry on close codes you have never seen before
Soak for an hour before you believe a latency number
Google Cloud
Two of these have stories behind them that are not on a slide. Echo: the translation plays out loud and the microphone hears it, so we stack browser AEC, echoTargetLanguage: false on the translate model, and a line in the system instruction — three layers, because the prompt is a hint and not a rule. Fragments: a Japanese term like クバネティス arrives as をク + バネティ + スに, so glossary matching on each message finds nothing; buffering across boundaries took the display found-rate from 52% to 87%.

If you take one thing: the demo is the easy part. Everything on this list only appears after the first ten minutes of continuous use, and none of it is visible in a thirty-second recording.
